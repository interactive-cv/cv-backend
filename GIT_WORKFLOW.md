# Git Workflow

Жёсткие правила git для ассистента и владельца проекта.
Нарушение = расхождение master и прода, потеря коммитов, сломанные ссылки.

---

## Жизненный цикл задачи

```
начало задачи → feature-ветка от master → коммиты → push → PR
→ CI зелёный → merge (владелец) → pull master локально → удалить ветку
→ начало следующей задачи
```

---

## Правила

### 1. Master — только через PR

- **Прямой push/коммит в `master` запрещён** (branch protection).
- Любое изменение — через feature-ветку → PR → merge.
- **Ассистент не может мерджить PR** — нет GitHub API-токена. Ассистент пушит ветку и **напоминает владельцу** сделать merge в GitHub UI.

### 2. Новая задача — новая ветка от актуального master

```bash
# Перед началом задачи — ВСЕГДА обновить master:
git checkout master
git pull origin master

# Создать ветку с осмысленным именем:
git checkout -b feature/short-name    # новая фича
git checkout -b fix/short-name        # багфикс
git checkout -b docs/short-name       # только документация
git checkout -b refactor/short-name   # рефакторинг без изменения поведения
```

**Конвенция имён:** `type/kebab-case-name`. Примеры: `feature/contest-artifacts`, `fix/nginx-timeout`, `docs/quickstart`.

### 3. Коммиты — атомарные с префиксом

- Один логический шаг = один коммит. Не «всё в один огромный» и не «каждая опечатка отдельно».
- Формат сообщения: `type: краткое описание`
  - `feat:` — новая функциональность
  - `fix:` — исправление бага
  - `docs:` — только документация
  - `refactor:` — рефакторинг без изменения поведения
  - `chore:` — сборка, зависимости, CI
- Тело коммита (опц.): что изменилось, зачем.

```bash
git add -A
git commit -m "feat: contest artifacts — upload APK, public /dl/{code}"
git push origin feature/short-name
```

### 4. PR — перед merge проверить CI

- Открыть PR на GitHub: `feature/short-name → master`.
- **CI должен быть зелёным** (ruff + pytest + tsc + build). Не мерджить с красным CI.
- Если CI упал — фиксить в той же ветке (`git commit --fixup` или новый fix-коммит), пушить, ждать CI.

### 5. После merge — синхронизировать локальный master

```bash
git checkout master
git pull origin master
git branch -d feature/short-name   # удалить слитую ветку локально
```

На GitHub — тоже удалить ветку (кнопка «Delete branch» после merge).

### 6. Два репо — синхронно

Если задача затрагивает и `cv-backend`, и `cv-frontend`:
- Создать ветки с **одинаковым именем** в обоих репо.
- Открыть PR в обоих.
- Мерджить оба (можно в любом порядке, но до деплоя — оба).

### 7. Hotfix — исключение для emergency

Если прод сломан (500, чат не работает) — деплой через `deploy.sh` сразу, без PR:

```bash
cd cv-backend && bash deploy.sh
```

**Но после** — обязательный PR «вдогонку», чтобы git-история догнала прод:
- Создать ветку `fix/hotfix-description`, закоммитить те же изменения, PR, merge.
- Иначе master и прод расходятся → следующий деплой откатит fix.

## Чек-лист (для ассистента)

Перед тем как сказать «задача готова»:

```
[ ] 1. Изменения закоммичены и запушены в feature-ветку
[ ] 2. CI на ветке зелёный (проверил через API или дождался)
[ ] 3. PR создан (или открыт)
[ ] 4. Владельцу явно сказано: «PR #N готов к merge» с ссылкой
[ ] 5. После подтверждения merge — git checkout master && git pull
[ ] 6. Локальная ветка удалена
[ ] 7. Следующая задача — от актуального master
```

## Чек-лист (для владельца)

Когда ассистент говорит «PR готов к merge»:

```
[ ] 1. Открыть PR по ссылке
[ ] 2. Проверить что CI зелёный
[ ] 3. Merge (Squash и Merge — на усмотрение)
[ ] 4. Delete branch на GitHub
[ ] 5. Сказать ассистенту «смерджил» — он обновит локальный master
```

## Антипаттерны (НЕ делать)

| Антипаттерн | Почему плохо | Правильно |
|---|---|---|
| Коммитить напрямую в master | Branch protection; расхождение с PR-флоу | feature-ветка → PR |
| Создавать ветку от устаревшего master | Потеря чужих коммитов; конфликт CI | `git pull origin master` перед веткой |
| Мерджить PR с красным CI | Сломанный master, упавший деплой | Фиксить до зелёного |
| Оставлять ветку после merge | Мусор, путаница «какая ветка активна» | `git branch -d` + delete на GitHub |
| Deploy.sh без последующего PR | Master расходится с продом | Hotfix → PR вдогонку |
| Один гигантский коммит на всю задачу | Тяжело ревьюить, тяжело откатывать | Атомарные коммиты по шагам |
| Забыть pull после merge | Новая ветка от устаревшего master | Пункт 5 чек-листа |
